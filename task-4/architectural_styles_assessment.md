## Задание 1. Оценка архитектурных стилей

### Событийно-ориентированная архитектура

* <u> Способ декомпозиции системы: </u>
 
* <u> Количество независимых единиц развертывания: </u>
 
* <u> Изменяемость кода (Code Modifiability): </u>
 
* <u> Изменяемость архитектуры (Architectural Modifiability): </u>
 
* <u> Сложность развертывания изменений (Change Deployment Complexity): </u>
 
* <u> Отказоустойчивость (Fault Tolerance): </u>
 
* <u> Архитектурная модульность (Architectural Modularity): </u>
 
* <u> Операционная модульность (Operational Modularity): </u>
 
* <u> Сложность разработки (Development Complexity): </u>
 
* <u> Производительность (Performance): </u>
 
* <u> Надежность (Reliability): </u>
 
* <u> Масштабируемость (Scalability): 5/5</u>

Плюсы:
* Подходит для пиковых нагрузок, так как очередь сглаживает пики

* Повышение числа запросов не обруживает сервер/БД, а ложатся в очередь, которую разгребают консьюмеры. Число консьюмеров можно увеличивать

* <u>Тестируемость (Testability): 2/5 </u>

Плюсы:

* Тестирование каждой отдельной компоненты не затруднено

Минусы:

* Тестировать потоки событий в E2E тестах крайне сложно
    * Тест отправляет событие и ждет неизвестное количество времени, пока оно пройдет через брокер, консьюмеров
    * Высокая вероятность Flaky-тестов
* Невозможно предсказать ожидаемое состояние системы при потоковой обработке


### Микросервисная архитектура

* <u> Способ декомпозиции системы: </u>
 
* <u> Количество независимых единиц развертывания: </u>
 
* <u> Изменяемость кода (Code Modifiability): </u>
 
* <u> Изменяемость архитектуры (Architectural Modifiability): v</u>
 
* <u> Сложность развертывания изменений (Change Deployment Complexity): </u>
 
* <u> Отказоустойчивость (Fault Tolerance): </u>
 
* <u> Архитектурная модульность (Architectural Modularity): </u>
 
* <u> Операционная модульность (Operational Modularity): </u>
 
* <u> Сложность разработки (Development Complexity): </u>
 
* <u> Производительность (Performance): </u>
 
* <u> Надежность (Reliability): </u>
 
* <u> Масштабируемость (Scalability): 4/5 </u>
 
Плюсы:
* Можно масштабировать каждую отдельную компоненту в зависимости от нагрузки
* Микросервисы в микросервисной архитектуре часто делаются идейно stateless => поддерживается горизонтальное масштабирование отдельных компонент
* Позволяет настроить разные стратегии масштабирования и балансировки нагрузки для разных микросервисов (повышать разные типы ресурсы, настраивать limit rps)
* Можно повышать масштабируемость отдельной компоненты сменой технологии конкретного микросервиса
* Архитектура позволяет измененить протокол взаимодействия с синхронных запросов на асинхронные позволяет выдерживать пиковые нагрузки
 
 Минусы:
* При синхронном взаимодействии масштабирование одного сервиса может просто "перенести" нагрузку на следующий микросервис по цепочке вызовов

* <u> Тестируемость (Testability): 3/5 </u>

Плюсы:

* Очень легко писать юнит-тесты (мокаем зависимости и другие микросервисы)
* То есть готова проверка каждого отдельного компонента системы и выполнения контрактов на входные-выходные данные

Минусы:

* E2E и интеграционные тесты писать сложно
    * Приходится поднимать окружение, состоящее из десятков микросервисов с их базами
    * Мокать зависимости или писать отдельные условия для цеклов (например, с пропуском этапа аутентификации)
    * Искать ошибки по логам в тестах сложно
